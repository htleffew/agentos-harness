# Roleplay Instructions extension-wide UX specification

**Status** Implementation in progress on `feature/extension-ux-consistency`

**Baseline** `feature/quick-replies-guided-turns` at `84225c07dabf298e0951247b1def19eac950ccc6`

**Design standard** November 2026 project baseline

## Goal and coverage

A first-time user can find a task on a phone, tell what the action will change and what it will cost, complete it, and return to the place they started. A user who learns that pattern in chat can predict the corresponding behavior in the panel, editors, and review screens. The work covers the 22 existing panel pages, the composer, reply cards and controls, shared editors and disclosures, and supported host handoffs. Roleplay Instructions is the extension. Roleplay Instructions V10 is its companion preset. A host has one active preset throughout each test run. [Interface map](../README.md#interface-map) · [Mobile UX standard](mobile-ux-standard.md)

Retain the five familiar groups, existing capabilities, persisted data, and story and model behavior as the implementation baseline. Consolidate duplicate interfaces onto a single owner for each task, with contextual entry points where they help. Keep intentional distinctions such as temporary direction, durable fact, draft preview, and model-assisted generation visible. Use the current system primitives before introducing shared code. Change storage only when an acceptance criterion needs it. [Repository guidance](../AGENTS.md) · [Quick actions handoff](quick-replies-implementation.md)

### Evidence and decisions

The prior audits establish several concrete findings. A reviewer initially looked for the extension in the host wand menu. Later cold review found ambiguous pinned actions, choices and errors below the visible region, reused Add form state, and fact search gated by replacement text. The 390 px sweep established that people could reach the panel controls through the tested paths. The accessibility run established focus, reordering, non-color cues and selected Orca disclosures at specific sizes. Keep those fixes as regressions. Transfer of learning across groups, terminology across entry points, and the remaining page-level opportunities in this specification are design hypotheses to check in the new baseline review. [Earlier independent review](ui-audit-10.0.32.md) · [Quick actions verification](quick-replies-verification.md) · [Accessibility evidence](audit-evidence-quick-actions/accessibility/README.md)

The canonical wording, navigation defaults, search behavior and study targets below are proposed implementation defaults. Record changes to these defaults with the observed reason and update the affected acceptance criteria. Track newly discovered opportunities under the affected ID or append an ID with its owner and test. [Design and review criteria](mobile-ux-standard.md#design-and-repair-criteria)

## Shared interaction contracts

| Contract | Required behavior |
| --- | --- |
| Destination and context | Give every page and task a stable internal identifier. Resolve a navigation request by group, page, task, and any supplied target. Track the origin surface and return point separately. Chat data is scoped to the chat and character or group. Reply work also carries the selected swipe and revision. Preset edits carry the host preset and the affected block or field. |
| Wayfinding | Group switches expose the active page. Each page and nested editor names its current task and, where useful, its ancestor and target. **Back** returns through the extension’s task history. **Close** dismisses the current surface and returns to its origin. The host browser’s history keeps its existing behavior. A cross-link opens the specific destination and gives a short path back to the initiating task. |
| Scope and ownership | Show the scope at the point of edit and save. Use **This reply**, **This chat**, **Extension defaults for this preset**, **Shared host preset**, or **Extension-wide** as applicable. For inherited values show the effective value and its source. Name the source used by every restore. Maintain ownership checks across delayed responses, imports and presets or chats changing while work is open. |
| Interaction semantics | A disclosure reveals information. A link or navigation button changes location. A checkbox or pressed button selects. A primary button commits the named outcome. Use native elements where possible and visible labels for meaningful actions. Use a shared icon meaning for the same action or state, with the same visible wording and accessible name. |
| Feedback and recovery | Keep draft, selection, target, open disclosure, and applicable scroll position through incidental redraws. On success show what changed and where. On failure leave the work available and show the reason and next action. Keep pending, running, completed, cancelled, failed and uncertain states distinct. Additional model work requires explicit action or a saved opt-in. |
| Mobile and accessibility | Fit the visible viewport, including the keyboard-open state. Keep primary, Back and Close reachably placed. Use the project’s 44 × 44 CSS px target for standalone controls. Keep labels and values legible at 320 CSS px, at 200% text size, and with long labels. Support keyboard navigation, sensible focus order and restoration, informative status announcements, reduced motion, visible focus, contrast and non-color states. Provide tap alternatives to gestures. Apply relevant WCAG 2.2 AA criteria. |

Reuse `app.openPage`, `app.openSetting`, the sheet’s chat-scoped state, shared DOM and execution controls, and the existing data writers where they meet these contracts. A route implementation may keep contextual state in memory. Use saved locations only for stable page IDs or user-authored settings, with a safe fallback for old or unavailable destinations. Avoid one router per feature. Keep tests against user-visible roles and outcomes, with IDs for exact target verification. ### Canonical task wording

Use these visible defaults across entry points. Keep familiar host wording such as “swipe,” “World Info,” and “impersonation” in secondary text or search aliases. Preserve user-authored labels and existing data identifiers.

| Intent | User-facing label and destination |
| --- | --- |
| Add temporary guidance for the upcoming reply | **Steer the next reply** opens the queue editor. **Queue with my next message** commits the snapshot. **Pending directions** opens the exact queued wording and its recovery controls. |
| Generate an alternate for a specific reply | **Generate an alternate reply** opens that reply’s guided editor. The editor identifies the selected **Version**, with “swipe” explained on first encounter. The final button states the generation action and any additional call. |
| Append to a reply | **Continue this reply** opens that version. Preview identifies the ending to extend and the availability of **Undo continuation**. |
| Prepare the user’s contribution | **Draft my reply** opens the draft editor. **Give me choices** requests alternatives. **Use this wording** puts editable text in the composer. The host Send action sends it. |
| Correct a source fact | **Correct story facts** opens **Story → Corrections** in the relevant chat and reply context. The editor offers a local **Repair facts only** path and a separately labeled **Repair facts and generate alternate** action where available. Existing source-edit capability remains explicit. |
| Review a specific reply | **Review this reply** opens the matching **What Was Sent** receipt. **Writing notes** opens its Notes section. The reply selector shows reply and version. |
| Review story filing or chapter coverage | **Context & Memory** owns filing and chapter status. Contextual links from Story World, chat and receipts open the relevant section or supported operation. |
| Change shared prompt or connection behavior | **Edit preset prompts** opens the active host preset workbench. **Model request settings** opens the relevant function and its resolved connection. Show the extension and host preset names separately. |
| Author or manage saved quick actions | **Manage quick actions** opens the library manager. **Browse directions** opens choices for the current family and scope. Distinguish **Pin**, **Select** and the action that queues or generates. |

Each package produces an implementation commit or a clearly scoped set of commits, a focused regression, and an audit update. Integration follows the dependency order below. Independent packages may use fixtures for the agreed navigation, ownership, and execution contracts. The integrator owns shared labels, routes, and the final combined test.

| Package | Work and likely entry points | Exit evidence |

## QA protocol

### Functional, touch and accessibility verification

Run the pinned-baseline and feature unit commands and reuse the existing real-host suites. Extend the 22-page audit to check current location, default hierarchy, keyboard-open reachability and return focus. Add targeted tests for same-task entry points and failure recovery. Use request captures around the interaction itself, not inferred counts from the UI. | Host and preset | Run SillyTavern with its built-in **Default** preset, then repeat with **Roleplay Instructions V10** as the active preset. Roleplay Instructions is the sole enabled extension in both runs. Run the optional named-profile path separately when the host service requires it. ### First-use and transfer study

Use at least eight first-time extension users as the proposed human study target, split between people familiar with SillyTavern and people new to it. Give them task goals and a populated phone-width fixture with no README or location hints. Rotate task order, preserve which tasks they see first, and use equivalent scenarios for repeat comparisons. Supplement with a fresh cold agent review during development. Document environment and sample for each group. [Usability testing guide](https://www.nngroup.com/articles/usability-testing-101/)

| Give the reviewer this goal | Observe and then test transfer |
| --- | --- |
| “You want the next reply to avoid the gate. Keep your own descriptive sentence in the composer.” | Discover, queue or adjust a direction, predict which tap sends. Then give a similar task on a prior reply. |
| “This reply has the right idea. Get another version and go back if you prefer the original.” | Locate the reply action, identify the target version, predict the call, compare versions and return. Then ask them to extend only that version. |
| “You want a few ideas for what you could say. Pick one and change it before sending.” | Find choices, edit, recover previous draft. Ask which action moves wording into the composer and which sends. |
| “The gate is closed. The chat keeps saying it’s open. Fix what the extension remembers.” | Find a source, locate Corrections and predict whether it will generate. Then view the result from a receipt and find the route back to the same source. |
| “Change how a single chat behaves, then undo it. Now show where you would change the shared default.” | Predict target and inheritance before touching the control. Apply the pattern to a preset field or a commentator voice. |
| “Tell me what ran and how to recover after it failed.” | Find the receipt and saved connection, predict retry cost, recover with the original draft. Then identify code, ordinary and extra request effects in a different part of the extension. |
| “Move a shortcut, export it, then bring it back and check what will change.” | Complete edit, reorder, preview and transfer by touch. Then find a comparable management operation in a book or prompt editor. |
| “You’ve returned to a long chat. Find what has been filed and what can still change.” | Find Context & Memory, read a coverage and status label, and identify a safe next action and the source or reply it affects. |

Target at least six of eight people completing each core task without hints and choosing the intended first destination or a mapped equivalent route. Target at least six of eight correctly predicting the outcome and scope of the paired task before activating it. Require zero unintended sends, extra model calls, or data losses caused by the interface in the study. Capture denominators, detours and assistance. Treat misses as design findings and retest affected tasks with a fresh reviewer. Report the outcome as evidence for the tested tasks and sample. Lack of access to users or native hardware leaves that evidence pending while implementation and available verification continue.

Define completion from visible outcomes and recorded state before the session. Count the first destination after entering the extension. Record a hint or intervention before assisting and preserve the unassisted outcome. For a comparison with the old interface, assign equivalent scenarios independently or counterbalance the interface order and report the two groups separately.

## Definition of done

- Each of UX01–UX20 and every inventory row has a pass, fail or unresolved evidence entry with a link to its test or finding. Each pass names the tested revision, host, preset, input, viewport and fixture. Navigation evidence includes actual entry, target and return actions. Source edits and model actions include before and after state.
- The combined build meets the shared interaction contracts. Every mapped action has a touch path from discovery through completion or recovery. Supported secondary actions, settings, import, export, scopes, and edit and restore controls are reachable with the keyboard open.
- Existing and new tests cover prompt, state and request compatibility, including imported and older saved data. Request captures establish execution stage, counts, retry, automatic opt-in, stable request assembly and preserved ownership. Fix any duplicate dispatch, corrupted state, data loss, inaccessible control or misleading call boundary before release.
- The release audit contains functional reachability, independent cold task and transfer results, accessibility observations, and separate device, webview, agent, human, mock and live-provider evidence as applicable. Each environment-dependent unknown is explicit. Apply the existing mobile release requirement for native mobile evidence. [Mobile UX standard](mobile-ux-standard.md)
- Fix discovered defects and rerun each affected and adjacent task. Record first-use failure causes and the result after the fix. Update UI help, README navigation, change notes and the final audit. The handoff names the implementation commit, test commands, captured evidence and remaining verification limits.
