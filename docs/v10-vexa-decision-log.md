## 2026-11-19 · Dice findings and agreed direction

| Question | Extension v9.0.1 | Vexa v1.0 |
| --- | --- | --- |
| Where does randomness come from? | One browser-generated d20 per enabled side on a fresh eligible reply. The default sides are the user, main character, and one shared roll for other characters. The random helper uses system randomness with a Math.random fallback. | SillyTavern dice macros request one user d20, four spotlight NPC d20s, and two World Sim d20s when evaluated. The world dice cover event triggering and event disposition or scale. World Sim asks the model to supply a missing seed as a fallback. |
| Who adjudicates? | Code calculates all stat totals and outcomes. The model chooses whether there are stakes, which stat fits, and how the result appears in prose. | The model decides whether a check applies, chooses a difficulty class, applies modifiers, and interprets the margin. The instruction says to choose difficulty first, but the model already sees the dice. |
| What does difficulty change? | There is no action-specific DC. The same total lands in the same outcome band. The bands are ≤2 bad failure, 3–7 failure, 8–11 partial success, 12–16 success, 17–21 strong success, and ≥22 brilliant success. No natural 1 or 20 override. | Difficulty affects the result. A 13 + 2 succeeds by 5 against DC 10 and fails by 3 against DC 18. Vexa also prescribes critical outcomes for natural 1 and 20. |
| What happens on a swipe? | Ordinary replacement paths normally reuse the same dice. The existing Pick again path can reroll dice and repick other orders. | The preset requests fresh rolls. Live behavior across swipes is open. |

**Why everything looked like a natural 1.** One d20 is reused across all six default stats for a side. Six rows showing 1 are one draw, with probability 1 in 20. A swipe can show that same draw again. Three independent sides all drawing 1 on a fresh reply would be 1 in 8,000. The helper produced 5,092 ones in a 100,000-draw local sample. This checks the helper, while **What Was Sent → Dice → Exact text sent** is the evidence for a specific turn. Model prose, Roast, or Vent may claim a different roll. The optional checker can comment when an order check already runs and does not independently audit the die or chosen stat. [Dice](../src/dice.js) · [Random helper](../src/books.js) · [Swipe and checker logic](../src/engine.js)

**Where the cost is.** One default sample contained 1,386 characters, about 350 estimated tokens before the wrapper. It spelled out twelve alternative stat outcomes even when no attempt needed a check. The random draw is cheap. The repeated prompt text, unused results, and model discretion after seeing the outcomes are the issues. Vexa passes a compact list of seeds, but adds its own adjudication and world-simulation instructions.

### Decided · Use explicit, code-resolved checks

- Make the check explicit. Commit the attempted action, actor, stat, and difficulty before revealing the die. Roll once outside the model and resolve the result in code.
- Send one concise result with the regular generation. Turns without a check should add zero action-dice prompt tokens in this mode. The manual workflow should require no extra model call.
- Record the raw roll separately from the modifier, total, difficulty, and outcome. Show the recorded result in What Was Sent and distinguish a resolved check from a pre-rolled option or model commentary.
- Preserve a resolved check across ordinary and guided swipes of the same turn. Provide a way to reroll just that check without repicking story events or orders. Keep action dice separate from story-event randomization.

Example receipt format, with provisional outcome wording: **Hale · Agility · DC 14 · d20 9 + 2 = 11 · minor failure.** Narrate the consequence while leaving the user’s next choice open.

### Proposed · Preset compatibility and optional dice mode

- For the initial pairing, let Vexa handle prose, action dice, NPC simulation, and plot timing. Use curated Story World facts, guided swipes, and What Was Sent from the extension. Start with extension action dice, Random Story Events, automatic World orders, Writing Style, and Roast off. Leave automatic chapter hiding off until a live request confirms the recent ledger survives.
- A small Vexa compatibility mode could detect its console in Auto, read its location and present characters as a fallback for selecting Story World notes, and exclude its ledger from prose-only chapter and checker inputs. Preserve normal history and avoid synchronizing the entire simulation ledger.
- Consider a compact pre-roll mode for spontaneous checks, especially NPC actions that have not been written yet. Show at most a compact result per enabled side and label these as available rolls. Treat it as a convenience with different guarantees from explicit checks.

### Open · Implementation and verification

- Choose how a check is entered and attached to the next reply, how difficulty and outcome bands work, and whether natural 1 and natural 20 have special rules. Vexa’s rules are a comparison point.
- Define pending checks, cancellation, failed generation, multiple checks in one turn, changes to the attempted action on a guided swipe, and branch or history edits. Decide how existing v9 stat sheets, settings, and saved roll records carry forward.
- Define what counts as a resolved check in What Was Sent and how dice-only rerolls interact with the existing rollback behavior.
- Test live Vexa rendering and both output blocks, the preset’s swipe dice behavior, the latest complete ledger after hiding and history changes, effective context limits, and the effects of a separate lean profile. The comparison used code inspection and a regex fixture, without a live combined-model run.
- Verify no dice rows on a turn without a check, one compact receipt for an explicit check, stable results on repeat or swipe, and a dice-only reroll that leaves other selections alone. Verify on SillyTavern and check TauriTavern separately where available.

### Proposed request and memory design

- **Stable prefix.** Version the shared preset, output contract, and any required tools or examples. Place stable character and persona material before volatile material where the host allows it. Keep roles, serialization, and tool order stable. Avoid expanding timestamps, dice, live state, and varying retrieval into early system blocks. Verify the actual wire order after SillyTavern or TauriTavern expands macros, resolves World Info, and inserts prompts by depth.
- **History and scene packet.** Keep clean append-only history through ordinary turns where useful. Put relevant state, linked evidence, scene-local guidance, and a resolved check near the live turn. A branch, edit, sliding-window removal, or compaction can legitimately cut prefix reuse. Refresh optional long-range layers at meaningful boundaries and keep the most recent truthful state available immediately. Benchmark append-only, chapter-based, and bounded-history layouts on representative chats. A moving injection inside history can break reuse before the end of the chat even when the preset itself is unchanged.
- **Use the archive selectively.** Keep the original text available. Retrieve using stable IDs, aliases, current scene, active agendas and threads, with lightweight lexical search as the starting point. Bring the setup and its later correction together. Include the relevant excerpt when tone, exact wording, or contradictory evidence matters. Make relevance decisions visible and offer a way to pin a fact. Summarize at useful boundaries or at the user's request. Do not depend on a fresh LLM planner, retriever, or checker for every turn.
- **One model request by default.** Existing lorebook, history, rollback, and prompt editor paths remain the foundation. Code handles validation, gating, arithmetic, rendering, and state storage. The normal reply contains prose and a bounded update only when something changes, using the existing format as the compatibility baseline. Treat model updates as proposals and apply them to the correct branch and reply only after validation. A malformed update should preserve previous state and leave the usable prose available. Reserve repair calls, drafting, and rollups for explicit or exceptional use, with costs visible.
- **Simplify Vexa’s prompt machinery.** Drop recurring full ledgers, map copy-forward, unused dice panels, visible planning transcripts, redundant prose audits, blanket vocabulary modules, conflicting model-specific blocks, and model-generated HTML/CSS as defaults. Replace the long script pipeline with structured updates and original extension-owned rendering. Keep the existing Vexa adapter proposal separate from the native companion preset so the latter can use one contract with one owner of state.
- **Measure attention and cache use separately.** Provider caching can reuse eligible prefix computation, while the cached text still takes context and can dilute relevant evidence. Use supported cache boundaries or cached-content objects, verify that the host forwards them, and never inflate a prompt merely to cross a cache minimum. Track cache read/write or cached input tokens where exposed, first-token latency, total input and output, calls per turn, and failure rates. Compare cold and warm runs, matched for provider/model and settings, including swipes and chapter rollovers.

### Verification and release order

1. Ship the smallest coherent native pairing first. Use a lean preset, code-resolved checks, one state update path, current scene and knowledge projections, and existing correction and rollback. Keep existing preset compatibility.
2. Use a fixed set of scenes to compare extension-only, Vexa-only, combined v9, and the native pairing. Include a quiet turn with no check, a hard check followed by confirmation and swipe, conflicting memories, a secret someone cannot know, a delayed Chekhov payoff, a branch, and a chapter rollover. Score prose and agency with human review. Verify state, dice, eligibility, and rollback with code assertions. Add Atlas validation when Atlas is in scope.
3. Add arc and agenda state, props, and an expanded console once the core works. Keep maps, quantitative relationship models, and optional commentary modular. Choose the final feature order after seeing which features improve continuity and play at acceptable cost.

## 2026-11-19 · Durable dialogue colors and realistic fiction guidance

**Status: Proposed.** Adapt the supplied realistic-fiction guidelines and neon palette into two features. Reuse the existing Story World voice field and prompt editors. Keep presentation preferences separate from character knowledge, personality, and story state.

### Speaker identity and rendering

- Store a persistent speaker ID and saved color preference. Link it to the Story World character or character card when possible. Give new recurring NPCs a chat-local identity first and allow promotion to the world roster. Resolve aliases against those IDs, keep ambiguous names unassigned until reviewed, and allow explicit merges and corrections. An alias, rename, change of mood, or move to another scene should not reassign a color.
- Reuse one validated speaker identity for dialogue, cast cards, and optional speaker labels. The model only needs the current speaker IDs or unambiguous aliases, and a short contract for identifying spoken spans. It need not see hex values, palettes, accessibility rules, or color-to-personality labels. Use simple semantic markup in the native preset. Parse known speaker references and optional supported cues, preserve visible text on malformed or unknown tags, and render with extension-owned CSS. Keep narration and internal thoughts in the host's normal text color.
- Add a read-only legacy adapter for supported Vexa tags and known preset formats such as the supplied font-color protocol. A bare hex is a visual hint, not reliable attribution. Preserve existing display behavior when identity cannot be established. Avoid double-rendering a span already handled by preset regex. Keep supported speaker markers or readable speaker names in history only where they clarify attribution. Strip presentation markup from prose-only consumers and keep the color palette out of prompts.
- For an unassigned character, favor colors perceptually distinct from the current cast and reserve persistent assignments for recurring speakers. Keep an established identity when colors run short. Reuse hues for minor speakers or use neutral text with a label. Speaker names or a text-label mode must remain available because contrast against a background does not establish distinction between speakers. Do not derive character traits or moral alignment from colors.
- Validate the effective foreground and background, including theme changes, overlays, and gradients. Preserve the saved palette choice and use a theme-appropriate rendering variant or normal readable text when the theme cannot be validated. Give the user a preview, an override, and a way to disable coloring. Branches should inherit the parent roster at the fork and keep new assignments and overrides isolated. Tie generated speaker attribution to the selected reply/swipe and allow a display correction without rewriting the dialogue.
- All 21 supplied swatches clear 7:1 on solid black, ranging from 8.47:1 to 17.43:1. Fifteen clear the preferred 10:1. All 21 clear 7:1 on the extension card's solid base #100E1C, while none clear 7:1 on white. Those are contrast measurements for flat backgrounds, not a claim of overall WCAG AAA compliance. [Enhanced contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-enhanced.html) · [Use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

### Writing guidance and durability

- Offer a versioned, editable **Realistic Fiction** preset profile with individual restore controls. Put the short style rules in the stable preset prefix. Reuse the existing Story World voice entry for durable rhythm, register, vocabulary, and habits, with a short user-approved example where helpful. Add the relevant cast's voice and knowledge cues to the changing scene context. Keep momentary mood separate. The current writer-wide rules mainly guide the extension's authoring requests, so give the profile an explicit live story scope.
- Preserve direct, concrete prose, restraint with figurative language, limited knowledge, organic revelation, distinct speech, and a turn ending that leaves the scene open. Use profanity and colloquial speech when they fit the speaker and scene. Let silence, hesitation, interruptions, and tonal shifts arise from motives and context. Avoid forcing every NPC to speak, exposing every private thought, demanding constant novelty, or putting louder punctuation everywhere.

Catch figurative cases like words that “landed” without banning literal files, invoices, or structural references. Highlight possible issues for review. Voice fidelity, a credible tonal shift, and whether a metaphor works remain qualitative judgments. Avoid automatic rewrites and extra model requests in the normal path.

## 2026-11-19 · Decision 15 · Seed recall with optional payoff scheduling

**Decided direction (2.5).** Retain organic recall and payoff, add optional per-seed gates, and evolve v9's existing world-order selector into configurable scheduling for selected seeds. The following details are proposed based on the v9.0.1 implementation.

- V9 already stores a planted detail, an optional payoff hint and planted/noticed/paid status. A model update can create a seed by title or mark it paid by title. Unpaid seeds compete for story-note space with a built-in relevance bonus and a recent-use penalty. Reminder selection is separate from selection for a payoff. [Seed storage and recall](../src/world.js) · [Update application](../src/worldflow.js)
- V9 can send a mandatory payoff order when the shared world-order roll passes (20% base chance by default) and an enabled, unlocked, unpaid seed meets a shared minimum age of six replies by default. A seed competes with other world orders and then for the overall reply cap. The payoff hint is wording for the model, without a code-enforced condition. The structured paid update changes status without retaining a payoff account. With checking off, a sent order can mark the seed paid without verifying that it happened in the reply. [Settings](../src/store.js) · [Selection and completion](../src/worldflow.js) · [Reply arbitration](../src/engine.js)
- Give each seed a stable ID, source reply, and optional scene, time, knowledge, or milestone prerequisites. Keep normal recall available for ungated facts. Gate a locked payoff separately from reminders about the setup, and withhold spoiler details until eligible. Leave scheduling optional per seed or set, with tunable weight and spacing if enabled. Old seeds can remain dormant or be retired without an invented resolution.
- Reuse shared scheduling and pacing rather than adding a competing event roll. A scheduled payoff normally gives the model an opportunity it can defer when the scene does not fit. The separately enabled Random Instructions path retains required directions. Record recalled, eligible, offered, and realized separately. Mark paid only when established by the selected reply or an explicit edit. Keep the payoff evidence and link it to any thread or fact it creates. Undo selected-reply effects on a guided swipe or branch.
- Verify recall of a locked setup without spoiler text, a time or knowledge gate, selection without completion, an organic payoff, and rollback of a completed payoff with checking disabled.

## 2026-11-19 · Decision 19 · Versioned updates within the reply request

**Decided.** Use one versioned story update alongside prose in the same generation request, with a reader for legacy v9 update blocks. Processing an ordinary reply's state must use zero additional model requests, including extraction, validation, fallback, repair, and migration of older records.

- Parse and validate changes locally. Bind results to the selected reply, respect protected fields and established prerequisites, and apply or roll back with the existing history rules. A reply with no state change can omit its update.
- If an update is absent, malformed, stale, or unusable, keep the readable prose and last valid state for the affected records. Continue play quietly. Diagnostics and voluntary corrections are available on demand. Do not call a model to reconstruct the missing change or treat it as established merely because an order was sent.
- When the extension can identify a failed or incomplete update that matters, it may request a small correction in the next normal generation's update block. Reference the relevant accepted reply and last valid state. Leave ordinary no-change replies alone. A repair should recover only what the accepted story establishes, respect newer state and protected edits, and be dropped if superseded or its source is swiped away. If repair still fails, retain the valid state and avoid an indefinite retry loop. The repair never triggers a standalone model call.
- Measure request counts for valid, absent, malformed, and legacy updates and for swipes. Existing separately configured features such as the optional instruction checker and chapter summarization remain separate from the state update path.

## 2026-11-19 · Decision 21 · Persistent, editable speaker colors

**Decided.** Use persistent speaker colors for dialogue only. Tone tags, kinetic effects, and motion are outside the v10 dialogue design. The player can inspect the currently assigned color and change it for anyone with an assignment at any time. Show a swatch and distinguish a theme-adjusted display color from the saved choice when they differ. Preserve stable speaker identity across aliases, scenes, and swipes. Apply contrast and accessible attribution rules locally.

- The native protocol identifies the speaker. The extension looks up the color and renders it. Accept any supported palette or custom valid color in the editor without passing palette values or display CSS to the model. Use the same stable identity for history and re-rendering. Verify assignment, override, aliases, and rendering after a theme change.
- Token check with the locally installed tiktoken package. Both cl100k_base and o200k_base encode the standalone strings cyan as 1 token, teal as 2, periwinkle as 3, and #40E8FF, #FF66F5, and #80C4FF as 5 each. The opening tag `<font color="teal">` is 7 tokens versus 9 for `<font color="#40E8FF">` on both encodings. These examples show a savings, not a universal rule. Count the entire serialized markup with the target model's tokenizer. A color word is not necessarily one token, and the measured encodings do not represent all supported models.
- Avoid a model-facing color protocol for native dialogue. Require only the minimum reliable speaker attribution. Compare short speaker labels or IDs with structured tags in realistic replies before selecting the native format. Legacy formats may use named colors where compatibility needs them.

## 2026-11-19 · Decision 23 · Standalone Roast with optional model feedback

**Decided.** Keep Roast opt-in and generate it in the normal reply request. Render it in a standalone card under the reply, collapsed by default and easy to open directly. This is a deliberate exception to Decision 20's tabbed layout for scene and character details. The Roast does not require a separate generation.

- Provide a separate opt-in for including recent Roast commentary in later story prompts. Display and prompt inclusion must be independently controllable. Use recent commentary from the active swipe and branch, and omit discarded or superseded Roast output.
- When included, label it as out-of-story voice feedback intended to encourage variety and counter repetitive or flattened portrayal. It may give the model a strong corrective contrast. It is not canon, character knowledge, or a direct state update. Keep the amount and lookback bounded. Do not use the commentary to override established facts or protected character profiles.
- Verify the standalone collapsed card, inclusion and exclusion in assembled prompts, no additional model request, and behavior across swipes and branches.

## 2026-11-19 · Decision 24 · One story contract with evidence-driven format adapters

**Decided.** Start with one shared model-facing reply format and one canonical extension state contract. Add a narrowly scoped adapter only when testing shows a repeatable format failure for a particular model and host. Connection profiles own model selection and supported API controls. Presets and writing guidance own differences in voice, pacing, and other prose preferences.

- An adapter pairs its request format with the matching reader. For example, if a model repeatedly fails to separate prose from a story update, a supported structured-response route could return separate prose and changes in the same generation. This is an example to verify when needed, not an adapter committed for any model.
- Normalize any supported format to the same extension contract. Apply the same validators, selected-reply binding, protected edits, rollback, and on-demand diagnostics. Keep one generation per regular reply and use the next regular reply for eligible repair under Decision 19.
- Verify that the host forwards any adapter-specific request options, that one applicable format is active, and that changing models or presets does not misread existing replies. Show the active format when an adapter is in use. Fall back to the shared format where the optional route is unsupported.
