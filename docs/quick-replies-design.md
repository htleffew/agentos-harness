# Quick replies and guided turns — discussion draft

**Status:** proposed for discussion, 2026-11-21. The [source audit](quick-replies-audit.md) inventories the six input files. The [four-repository review](quick-replies-reference-review.md) documents additional workflows and observed behavior in SillyTavern. The user has requested the capabilities below. The suggested defaults, data structures and milestones are open decisions. Implementation begins after review.

## The three jobs in the chat menu

**User decisions, 21 November 2026.** Quick access during play is the priority. The menu should support a large, editable catalog with three primary destinations. The user can act on a saved direction immediately, write free text, or combine saved directions and free text in the same request. Book browsing and local rolls are primary ways to choose a direction. A model-assisted player draft writes only the active user's part. Director plans, delayed surprises and revision pipelines remain available for separate discussion.

| Entry point | Primary button | Result |
| --- | --- | --- |
| On the newest eligible character reply | **Guide a swipe** | Generate a new alternate for that reply using the chosen guidance. The earlier swipe stays available. |
| Beside the composer | **Steer the next reply** | Attach one or more directions to the next message the user sends. The composer remains available for their dialogue. |
| Beside the composer | **Draft my reply** | Generate a context-aware player response now. The user can use, edit, regenerate or discard it before sending. |

All three are reachable from **Quick actions**. Guided regeneration uses the same cue and free-text editor as a guided swipe. Prefer a new alternate by default so the user can go back to the original. If using host Regenerate in place, label that effect explicitly and retain an undo baseline. Opening from a message preselects that message and its current swipe. The sheet opens on the selected job with pinned and recently used actions in reach, followed by search and **Browse all**. Browse groups the catalog by type, then set, entry and version or recipe ingredient as applicable. Users can pin a particular version, a whole set, or a roll with a saved scope. Keep library management under **Manage**. All controls have visible names and work without long press, hover or an open keyboard.

**Proposed interaction.** A favorite has a primary action and a labeled **Customize** control. On the swipe sheet, tapping the favorite can run that swipe immediately. On the steer sheet it queues the nudge with Undo. On the draft sheet it requests an editable draft. Customize opens the same sheet in selection mode. Tap any combination of compatible buttons, remove or reorder them, add optional **Your direction**, then tap **Generate swipe**, **Queue with my next message** or **Generate my draft**. Typing first and then selecting a button must preserve the text. If there is pending free text or a selection, tapping another template adds it. It never dispatches behind the user's back. With free text alone the same primary action works. Per-action execution and layout are recommended defaults awaiting review.

### Guide a swipe

The starter shelf contains **More emotional**, **More romantic**, **Bring in conflict**, **Add a plot twist**, **Back to character**, and **Fix world facts**. Each has an editable full prompt, a customization indicator and its own Restore. The same cue can have different wording for the player and NPC destinations. Assemble selected prompts once in display order, then append the user's free text as the most specific direction. Preserve literal user input and make the resolved wording inspectable. Compatible presets require no special tags or extra planning call.

* Choosing **Back to character** grounds the request in the responding NPC's card, established voice and recent behavior. **More emotional** can change what that NPC chooses to say or do while respecting the current scene.
* Choosing **Fix world facts** alone requests a consistency pass against applicable established facts. A specific correction such as “The south gate is still closed” feeds the existing correction and guided-swipe workflow. A generic button press cannot establish which stored fact is wrong. Persist a source correction only when there is a supported change. Show source changes and undo independently of switching swipes. Disclose any separately invoked source-repair call.
* Example: select **More emotional** and **Back to character**, type “Let the captain show relief through what he does. Keep his answer terse,” then generate once. Accepting the alternate reconciles the replaced swipe's extension-owned effects. The user's unsent message and separately queued next-message nudges survive.

### Steer the next reply

Offer extension instructions, writing styles, story events, linked story records, standalone nudges, and available native actions with a known delivery contract. **Dress me** is an example of an outfit direction. Resolve a user's installed shortcut when available. Also offer an editable extension-owned equivalent that can be queued as plain guidance. Display the origin so a native script with its own side effects is only executed deliberately. The action can specify its subject, including the active player persona.

Let a user pick an exact entry or version, draw from a single set, draw from a functional category such as Story Events across its eligible sets, or **Roll across everything** eligible for this destination. Within an event recipe, support choosing or rolling its individual ingredients. Show the pool and selected source. Recommended default for a broad roll is one ticket per eligible entry, followed by the existing version or recipe resolver. A 21-version instruction should not get 21 times the odds of a single-version instruction. Source weights and equal odds per set are separate distribution choices. Filtering, drawing, rerolling and queuing require zero model calls.

Each queued item specifies its treatment: **Nudge** for a preference, **Required direction** for something the character reply should accomplish, and its delivery format (private guidance/system note or visible OOC). Make the selected format obvious. Bind it to this chat's next actual user send and the character reply to that send. Drafting, previewing, swiping an earlier reply and background calls leave the queue intact. The send operation takes a snapshot of pending items. On retry it reuses the snapshot, including any visible OOC already appended, without duplicating the text. Cancelling before send removes an item without touching the player's draft. A receipt can confirm inclusion where the host exposes the request. Filing a new story fact requires evidence in the accepted fiction.

### Draft my reply

Starter buttons include **Respond naturally as me**, **Do something bold**, **Introduce an NPC**, **Initiate an intimate moment**, **Continue an intimate moment**, and **Introduce a plot twist**. **Introduce a plot twist** has an optional type picker, for example a revelation, reversal, interruption, misunderstanding or unexpected arrival, plus **Choose for me**. A user can add their own types or link a compatible twist recipe. Choosing a type, rolling one locally, or leaving it to the drafting model needs no preliminary suggestion call. A separate explicit “give me alternatives” action may request a batch.

For every template, assemble one request with the active player persona's name, description and applicable player facts; the player's recent dialogue and decisions; the scene and its present cast; relevant information the player can know; any current composer fragment; selected directions and free text. Label who supplied each input. Bound history to the target turn, honor hidden-history and knowledge boundaries and avoid spending pending character-turn nudges. With sparse persona data, rely on the available player-authored text and current scene. An unrelated preset or missing persona description does not disable drafting.

The draft contains only the player's dialogue, thoughts where appropriate, and voluntary actions. It can introduce someone through what the player does (“I hold the door and call my former partner over”), open an intimate moment through an invitation, continue through the player's response, or introduce a twist through a player-held revelation. It leaves other characters' answers, inner states and reactions available for their own turn. If the user wants the *world* to produce a stranger or a revelation independently, **Steer the next reply** can force that event in the NPC response. Both choices belong in the menu.

Example: select **Do something bold** and **Introduce a plot twist**, choose **Revelation**, add “I admit the letter is mine, in front of everyone,” and tap **Generate my draft**. One helper call writes the player's part in their established voice. Preserve the existing fragment and candidate separately. **Use draft** places the chosen text in the composer; **Try again** runs one more requested round. The user decides when to send. Discarding a candidate leaves chat history, lorebooks, queued events, dice and the original fragment untouched.

### Actions and costs

| Action | Proposed result | Additional model requests |
| --- | --- | ---: |
| Insert my text | Insert at the selection in the user's draft, with undo. Explicit **Send now** uses native send. | 0 for insertion; sending starts the ordinary reply |
| Direct next reply | Queue, inspect, change or cancel guidance for the reply to the next user send. Optional visible OOC uses an explicitly selected destination. | 0 beyond ordinary generation |
| Choose or roll from a set | Pick an entry/version or recipe ingredients, lock desired choices, roll remaining choices and preview exact text. Show unavailable reasons and linked source. | 0 |
| Use seed, secret, thread or twist | Select a particular record, choose among eligible records, or roll. Choose how the story may use it. For secrets default to foreshadowing. Explicit reveal names who may learn it. A standalone twist can exist without a lorebook record. | 0 |
| Roll an action outcome | Optionally attach one code-generated outcome and a short instruction to honor it. Display die, modifier, target when applicable and total. Reuse the existing action-check rules. Roll-once versus reroll is explicit on a swipe. | 0 |
| Draft my reply | Give direction or select an idea, choose the user's perspective, generate a candidate, edit it, request another round or insert it into the composer. Preserve the original draft and each candidate until dismissed. Sending the chosen draft is a separate action. | 1 per requested drafting round |
| Suggest directions | When explicitly requested, give the model a direction and request several choices in one response. Edit, choose or roll from the returned set locally. | 1 per requested batch |
| Force a story event | Select an existing event, enter your own, or explicitly commission one. Preview and append it to the **next character request** after the next user send as a required order. A separate **Revise this reply** action uses a guided replacement. | 0 for existing or authored text; 1 optional authoring call; a replacement uses the normal swipe request |
| Guide a swipe or revise wording | Choose the eligible reply, provide direction, decide which prior orders and rolls to retain, request one replacement and inspect its effects. A proposed text-only revision offers an original/revised view and an explicit accept operation. | 1 ordinary generation per guided swipe; 1 per explicitly requested rewrite pass |

Spell out the distinction between a required direction and a verified event. The extension can verify inclusion in an observable outbound prompt; a model can still omit the event. Offer the existing checker when appropriate and preserve its visible cost. Advance the story record only on accepted evidence. Browsing, pinning, resetting, choosing and rolling need no model connection.

## Library, variables and reversibility

1. **Built-in actions** have stable IDs, installed template revisions and independent overrides. Show Default, Customized and Updated default available. Each has restore, preview of the change and undo. Voice, preset, and other quick actions keep their own overrides.
2. **Linked actions** reference extension sets or world records. The catalog is generated from available sources; only pinned or customized records need durable shortcuts. Track physical book identity, logical set, entry UID and a content/identity check. Track category/item IDs where available; instruction versions lacking stable IDs need explicit reconciliation after a reorder. Never silently rebind a shortcut by title. Offer **Relink**, **Follow source**, **Edit source** with scope visible, and **Make standalone copy**.
3. **Standalone actions** support create, rename, duplicate, edit, delete/undo, order, enable, export and import using extension JSON. Save a creation or import baseline and label that restore target explicitly. Retain edits across upgrades. Optional per-chat overrides and library defaults show which value wins.
4. **Variable picker** separates current character/user and card fields, live book/record references, user-supplied parameters, and a roll result. Proposed typed slots include selected seed, secret, twist, instruction/version, style recipe and event recipe. Show availability, owning book, visibility, resolved text and empty-state behavior. Reuse supported host substitutions where available; show unresolved tokens and ask for a replacement or allow literal text explicitly. Treat standalone text as data. Native QR scripting is a separately chosen interoperability action.
5. **Originals and history** distinguish Restore built-in, Restore imported, Follow live source, Cancel pending, Undo last library edit and Undo an accepted story change. Restoring an action definition must preserve unrelated library edits, external books, other chats and accepted story history. Keep exportable backups and revision references so a deliberate shared-source modification can be reversed independently. Show the extent and limits of undo before bulk changes.
6. **Native QR import** first inventories visible and hidden entries, automatic triggers, commands, model calls, writes and dependencies. For Keel offer mappings for one-shot nudges, prompts and status links. Expose remaining entries as requiring native execution or a specific unmapped dependency. Keep preserved script text exportable. Import alone performs zero script execution, automatic registrations, worldbook writes or model requests. Round-trip IDs and unknown metadata for native exports where supported. Arbitrary native scripts can have side effects outside extension undo; label this before linking a native execution button.

## Preset independence and prompt visibility

The standalone composer, library, local rolls, native-QR inspection and draft generation should have no companion-preset-name check. Resolve feature availability using the active host API, chat, current target and available records. A user choosing Memory only can separately opt into explicit quick directions while keeping ordinary automatic writing modules off. Without an eligible story book, offer standalone actions and show where a linked action can be connected. A missing host hook disables the affected destination with a reason; preserve the draft and queue.

Pair editable quick-action prompts with known preset blocks in the existing workbench. Include provenance, affected turn, role/placement where supported, lifetime and estimated size. For other extensions distinguish observed active hooks/registered injections, user-declared overlaps and unavailable information. A similarly named block is a candidate, not proof of duplicate delivery. Expose independent choices for the quick action and any editable preset block. Cross-extension ownership relies on the other tool's published controls. Keep user-initiated comparisons optional. Restoring our settings should reverse only changes whose origin is known. An uninspectable preset still permits supported actions and shows the visibility limit.

## Implementation sequence

| Milestone | Proposed implementation and boundary | Exit evidence |
| --- | --- | --- |
| 1. Catalog and source adapters | Add a versioned action library alongside extension settings, plus per-chat pins, overrides, queue and turn references in chat metadata. Normalize native books using existing book/event/world readers. Read from a shared physical book once per revision. Invalidate on edits, chat changes and imports. Export definitions without private resolved chat data by default. | Six fixture inventories, source rename/move/delete tests, migration and round-trip results |
| 2. Pure resolution | Extract a side-effect-free version draw from the current mutating picker. Evaluate recipes through existing category, lock, burn, weight, pacing and no-repeat logic on a copy. Resolve typed arguments and optional physical dice in code. Return selected source IDs, exact text, draw and proposed state changes. | Preview/cancel causes zero writes. Selected and rolled results reproduce the displayed instruction. |
| 3. Chat UI and one-shot delivery | Add launcher, catalog, inspector, pending chips and manager. For a next-message direction, snapshot the queue on user send and bind it to the resulting character generation by chat, user message, target, swipe and attempt. For a message-level swipe, compose only the cues selected for that replacement. Reserve a stable selection, deduplicate the same automatic/manual source, then commit once on accepted completion. Release on failure or cancellation. Keep quiet, impersonation and dry-run requests ineligible. | Request captures, receipt, abort/retry and double-tap checks |
| 4. Guided drafting and replacement | Reuse logged AI request transport with explicit profile, bounded context and one-call mode. Preserve persona, speaking perspective, draft selection and prior candidates. For recorded replies call the existing guided transaction. Add a host-only path for an unrecorded reply that first inventories any extension-owned state requiring reconciliation. Make a new swipe or revision only after an explicit action. | Output stays in the intended chat; selected swipe, world facts, dice and chapters reconcile |
| 5. Interoperability and restoration | Capability-detect native QR enumeration and named execution. Add the import report, ownership inspection, per-item comparison and restore. If selected, the delayed direction, persistent guide and prose-revision capabilities below each get an independent implementation milestone and call budget. | Keel import with native QR enabled/disabled; opaque-host and concurrent-extension tests |
| 6. Validation | Use an isolated SillyTavern user, a request-recording endpoint and synthetic books with the uploaded shapes. Run a cold usability review on phone width and desktop. A live provider comparison can separately assess writing quality. | Durable audit listing actual clicks, requests, side effects, failures and fixes |

**Turn lifecycle.** Draft → queued → reserved by one eligible generation → accepted or released. Anchor records to the originating chat and selected swipe, including a content fingerprint so stale drafts can be recognized. A failed or empty generation returns the same reserved choice to pending. A retry should show whether the original request may already have reached a provider. A branch inherits accepted history through its fork point; pending parent directions require explicit copying. Batch deletion or editing invalidates stale receipts/effects through existing history reconciliation. An in-flight draft that finishes after a chat switch goes back to its originating draft store. It must never populate another chat’s composer.

## Decision log for discussion

These defaults remain proposals until chosen. Record each answer here before the build. The candidate inventory is open for discussion. The user has prioritized the three workflows above. Exact tap behavior, sampling weights and the scope of the secondary tools remain open.

| Decision | Proposed starting point | Other choices to compare |
| --- | --- | --- |
| D1. What a tap does | Per-action destination. Known nudges queue on tap with Undo; player drafts go to the composer; actions that call a model clearly say so. Long press is optional; a visible Edit/Preview control is always available. | Always preview first; always insert into composer |
| D2. Manual vs automatic eligibility | Explicit selection bypasses scheduling chance/cooldown once, preserves disabled entries, protected facts, constraints and user locks. Show that it was manually invoked. | Enforce all automatic eligibility; offer a per-action override |
| D3. Multiple pending directions | Visible ordered list; collapse exact duplicates. A user can replace an earlier action explicitly. | One shared slot like Keel; independent slots by category |
| D4. Dice and forced events | Separate choosing content from resolving an action. Default to a single fixed draw per requested turn. | Roll only on commitment; reroll on every swipe |
| D5. Guided drafts, costs and duration | Optional one-call candidates with editable direction and perspective. User sends the final draft. | Immediate impersonated send; optional multi-round or multi-pass chains |
| D6. Source management and restore | Live links by default, standalone copies on demand; show baseline and history scope. | Snapshot on pin; user chooses link or copy for each import |
| D7. Interoperability | Translate recognized actions, inventory all others, offer explicit native delegation when supported. | Extension-native library only; broad native script execution as a separate advanced mode |
| D8. Visibility and layout | One launcher plus user pins; show the pending count and destination. | Persistent category bar; message-level actions only |
| D9. Idea generation and directing | Keep “offer alternatives,” “combine directions into one scene” and “develop these ordered beats” individually selectable. | Local book draw only; generate on demand; generate a batch automatically after chosen replies |
| D10. Delayed directions | Track when a direction becomes due, is reserved, reaches the request and is accepted. Allow local book draws and optional generated surprises. | Fixed or random delay; concealed or visible content; optional recurring preparation with its own call budget |
| D11. Standing guides and trackers | Use a named, editable chat guide with visible lifetime. Reuse our existing world records when they own the same fact. | Static guide; scoped guide with expiry; optional model-refreshed guide; link to an external tracker |
| D12. Revision and continuation | Expose full-reply swipe, append-only continuation and reviewable prose revision as separate operations. | One pass; a user-defined sequence of passes; delegate to a compatible installed postprocessor |
| D13. Historical context | Resolve historical suggestions and revisions against the chosen swipe and its prior timeline. Show included lore and what the player character can know. | Deliberate retrospective mode; selected extra sources; user-specified context window |
| D14. Composition and group targeting | Allow insert, append, replace, visible send and private direction. Bind a group reply to a named member or a user-selected rule. | Composer only; allow explicit send without generating a reply; group-wide direction; delegate speaker selection to host |
| D15. Editing and restore scope | Show what changed on the shortcut, source prompt, generated option, player draft, or accepted reply. Restore the selected object from its recorded baseline. | Keep one baseline per object; retain revision history; follow a user's live source |
| D16. Exposing the tools | Give phone-visible names to the source and the result of tapping. Independently enable or pin each chosen operation. | Composer launcher; message-local picker; native Quick Reply linkage; all three as user-selectable entry points |
