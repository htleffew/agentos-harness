# Quick replies and guided turns — discussion draft

**Status:** proposed for discussion, 2026-11-21. The [source audit](quick-replies-audit.md) inventories the six input files. The [four-repository review](quick-replies-reference-review.md) documents additional workflows and observed behavior in SillyTavern. The user has requested the capabilities below. The suggested defaults, data structures and milestones are open decisions. Implementation begins after review.

## Supported setup

**User decision.** Exactly one host preset is active at a time, chosen by the user, and Roleplay Instructions is the only active extension. Switching from Vexa to the companion preset is a normal change of preset. The extension owns the quick-action menu, buttons, scheduling, drafting, guided swipes, correction and memory workflows. It uses core host services such as the composer, generation, swipes, preset settings and World Info. Every supported action must work with all other extensions disabled, including the bundled Quick Reply extension. The four reference projects inform behavior and UX; sample files such as Keel can be imported as data. Any supported imported behavior executes within Roleplay Instructions. The workbench compares the one active preset with this extension's modules.

## Mobile-first interaction

Use the [mobile UX standard](mobile-ux-standard.md) for design, repairs and interactive QA.

Design every extension surface for touch at phone width first, including chat actions, reply cards, editors, setup, receipts and logs. Expose help, secondary actions and status details through visible tap controls. Use the same controls on desktop with keyboard operation and accessible names. Give interactive icons a touch target of at least 44 × 44 CSS pixels. Let dense rows wrap and keep actions reachable with the on-screen keyboard open. Use labeled Move up and Move down controls wherever drag-to-reorder is available.

## The four guided feature families

**User decisions, 21 November 2026.** Quick access during play is the priority. The menu should support a large, editable catalog with four feature families. The user can act on a saved direction immediately, write free text, or combine saved directions and free text in the same request. Book browsing and local rolls are primary ways to choose a direction. A model-assisted player draft writes only the active user's part. Quick actions should reuse the existing scene, pacing, plot and autonomous event logic. The narrower authoring choices for plans and delayed directions are recorded in D9 and D10. Use automatic screening and next-turn guidance for routine prose issues.

| Feature family | Primary action | Result |
| --- | --- | --- |
| Guided generation | **Steer the next reply** | Attach one-use guidance to the reply to the user's next message. |
| Guided regeneration | **Guide a swipe** | Generate an alternate version of the targeted reply. |
| Guided continuation | **Continue this reply** | Append a new passage to the selected reply with optional cues and free text. |
| Guided impersonation | **Draft my reply** or **Give me choices** | Generate an editable first-person player draft or a set of player choices. |

All four are reachable from **Quick actions**. Guided regeneration uses the same cue and free-text editor as a guided swipe. Prefer a new alternate by default so the user can go back to the original. If using host Regenerate in place, label that effect explicitly and retain an undo baseline. Opening from a message preselects that message and its current swipe. The sheet opens on the selected job with pinned and recently used actions in reach, followed by search and **Browse all**. Browse groups the catalog by type, then set, entry and version or recipe ingredient as applicable. Users can pin a particular version, a whole set, or a roll with a saved scope. Each menu exposes its own Add control. **Manage** handles collection-wide changes. All controls have visible names and work without long press, hover or an open keyboard.

**Proposed interaction.** A favorite has a primary action and a labeled **Customize** control. On the swipe sheet, tapping the favorite can run that swipe immediately. On the steer sheet it queues the nudge with Undo. On the draft sheet it requests an editable draft. Customize opens the same sheet in selection mode. Tap any combination of compatible buttons, remove or reorder them, add optional **Your direction**, then tap **Generate swipe**, **Queue with my next message**, **Continue this reply** or **Generate my draft**. Typing first and then selecting a button must preserve the text. If there is pending free text or a selection, tapping another template adds it. It never dispatches behind the user's back. With free text alone the same primary action works. Per-action execution and layout are recommended defaults awaiting review.

**Guided actions are single-use (decided).** A cue, checked modifier or free-text direction belongs to the operation the user invokes. Clear the active selections after successful use. Keep reusable button definitions, named variations and saved drafts. A queued nudge waits for its intended turn, then retires. A failed attempt may be explicitly retried against the same target. Regular sends, unrelated swipes, reopens and subsequent drafting rounds never automatically reapply a spent cue. A user can deliberately reuse a button or expand a chosen CYOA option with its original direction. Accepted story facts and source corrections have their own lifetimes. Existing automatic book rules retain their separately configured timing.

### Guide a swipe

The starter shelf contains **More emotional**, **More romantic**, **Bring in conflict**, **Add a plot twist**, **Back to character**, and **Fix world facts**. Each has an editable full prompt, a customization indicator and its own Restore. The same cue can have different wording for the player and NPC destinations. Assemble selected prompts once in display order, then append the user's free text as the most specific direction. Preserve literal user input and make the resolved wording inspectable. Compatible presets require no special tags or extra planning call.

* Choosing **Back to character** grounds the request in the responding NPC's card, established voice and recent behavior. **More emotional** can change what that NPC chooses to say or do while respecting the current scene.
* **Fix world facts** invokes the shared Correct facts audit, propagation and repair workflow described below. It can run alone, or alongside tone and plot cues and optional free text. Its editable prompt controls wording; the operation itself is registered in code so changing the wording cannot silently disable source repair.
* Example: select **More emotional** and **Back to character**, type “Let the captain show relief through what he does. Keep his answer terse,” then generate once. Accepting the alternate reconciles the replaced swipe's extension-owned effects. The user's unsent message and separately queued next-message nudges survive.

### Steer the next reply

Offer extension instructions, writing styles, story events, linked story records and standalone nudges. **Dress me** is an editable extension-owned outfit direction. It can target the active player persona and can be queued immediately in a fresh installation.

Let a user pick an exact entry or version, draw from a single set, draw from a functional category such as Story Events across its eligible sets, or **Roll across everything** eligible for this destination. Within an event recipe, support choosing or rolling its individual ingredients. Show the pool and selected source. Recommended default for a broad roll is one ticket per eligible entry, followed by the existing version or recipe resolver. A 21-version instruction should not get 21 times the odds of a single-version instruction. Source weights and equal odds per set are separate distribution choices. Filtering, drawing, rerolling and queuing require zero model calls.

Each queued item specifies its treatment: **Nudge** for a preference, **Required direction** for something the character reply should accomplish, and its delivery format (private guidance/system note or visible OOC). Make the selected format obvious. Bind it to this chat's next actual user send and the character reply to that send. Drafting, previewing, swiping an earlier reply and background calls leave the queue intact. The send operation takes a snapshot of pending items. On retry it reuses the snapshot, including any visible OOC already appended, without duplicating the text. Cancelling before send removes an item without touching the player's draft. A receipt can confirm inclusion where the host exposes the request. Filing a new story fact requires evidence in the accepted fiction.

### Continue this reply

Offer the same editable buttons and optional free text as a guided swipe. Preserve the accepted prefix verbatim on the targeted message and swipe. Store the append boundary and the new scene and book effects. **Undo continuation** restores the preceding revision and reconciles just the appended passage’s effects. Verify the target revision before applying a delayed result or undoing across a later manual edit. Appending starts one ordinary continuation request and keeps the same story-turn slot.

### Draft my reply

Starter buttons include **Respond naturally as me**, **Do something bold**, **Introduce an NPC**, **Initiate an intimate moment**, **Continue an intimate moment**, and **Introduce a plot twist**. **Introduce a plot twist** has an optional type picker, for example a revelation, reversal, interruption, misunderstanding or unexpected arrival, plus **Choose for me**. A user can add their own types or link a compatible twist recipe. Choosing a type, rolling one locally, or leaving it to the drafting model needs no preliminary suggestion call. The same menu includes the primary **Give me choices (CYOA)** action described below.

For every template, assemble one request with the active player persona's name, description and applicable player facts; the player's recent dialogue and decisions; the scene and its present cast; relevant information the player can know; any current composer fragment; selected directions and free text. Label who supplied each input. Bound history to the target turn, honor hidden-history and knowledge boundaries and avoid spending pending character-turn nudges. With sparse persona data, rely on the available player-authored text and current scene. An unrelated preset or missing persona description does not disable drafting.

Write in first person (I, me, mine) from {{user}}’s limited point of view throughout player drafting, including playable CYOA text and expansions. Ground perception in what the player can ordinarily see or hear from their position, remember, or was told. The player may suspect a motive based on an observable cue; never present another character’s private thoughts or unseen events as the player’s knowledge. The draft contains only the player's dialogue, thoughts where appropriate, and voluntary actions. It can introduce someone through what the player does (“I hold the door and call my former partner over”), open an intimate moment through an invitation, continue through the player's response, or introduce a twist through a player-held revelation. It leaves other characters' answers, inner states and reactions available for their own turn. If the user wants the *world* to produce a stranger or a revelation independently, **Steer the next reply** can force that event in the NPC response. Both choices belong in the menu.

Example: select **Do something bold** and **Introduce a plot twist**, choose **Revelation**, add “I admit the letter is mine, in front of everyone,” and tap **Generate my draft**. One helper call writes the player's part in their established voice. Preserve the existing fragment and candidate separately. **Use draft** places the chosen text in the composer; **Try again** runs one more requested round. The user decides when to send. Discarding a candidate leaves chat history, lorebooks, queued events, dice and the original fragment untouched.

#### Give me choices (CYOA)

**User decision.** Choose-your-own-adventure is a required player impersonation feature. Put **Give me choices** next to **Generate my draft** on the main Draft my reply sheet, visible on first use with any preset. One tap with empty guidance requests several distinct, immediately playable things the player could say or do next in this scene. Use the active persona, recent player behavior and player-accessible knowledge. Leave NPC reactions and the outcome open.

Before tapping, the user may tick one or more cues such as **Make it more dramatic**, type a direction, do both, or do neither. All four combinations are valid. In the CYOA controls, ticking is selection only. Typing, changing a tick, opening the sheet, or receiving a new reply starts zero requests. On **Give me choices**, snapshot the selected cues and text together and generate the batch in one helper call. After successful use, keep the inputs on that batch for inspection or explicit reuse. A fresh batch starts with clear guidance. The CYOA prompt has the same inspect, edit, variation and restore controls as other impersonation prompts.

Selecting or editing a choice costs zero calls. **Use this wording** inserts it in the composer with draft recovery. **Draft from this choice** explicitly spends one additional call to expand the chosen action in the player’s voice, retaining the direction that produced it. The user decides when to send. Browsing, dismissing or rolling within the batch leaves the conversation, story facts, and next-message nudges untouched.

Offer the existing checker when appropriate and preserve its visible cost. Advance the story record only on accepted evidence. Browsing, pinning, resetting, choosing and rolling need no model connection.

## Library, variables and reversibility

1. **Built-in actions** have stable IDs, installed template revisions and independent overrides. Show Default, Customized and Updated default available. Each has restore, preview of the change and undo. Voice, preset, and other quick actions keep their own overrides.
2. **Linked actions** reference extension sets or world records. The catalog is generated from available sources; only pinned or customized records need durable shortcuts. Track physical book identity, logical set, entry UID and a content/identity check. Track category/item IDs where available; instruction versions lacking stable IDs need explicit reconciliation after a reorder. Never silently rebind a shortcut by title. Offer **Relink**, **Follow source**, **Edit source** with scope visible, and **Make standalone copy**.
3. **Standalone actions** support create, rename, duplicate, edit, delete/undo, order, enable, export and import using extension JSON. Save a creation or import baseline and label that restore target explicitly. Retain edits across upgrades. Optional per-chat overrides and library defaults show which value wins.
4. **Variable picker** separates current character/user and card fields, live book/record references, user-supplied parameters, and a roll result. Proposed typed slots include selected seed, secret, twist, instruction/version, style recipe and event recipe. Show availability, owning book, visibility, resolved text and empty-state behavior. Reuse supported host substitutions where available; show unresolved tokens and ask for a replacement or allow literal text explicitly. Treat standalone text as data. Imported command strings remain inert data. Only mapped extension operations can be invoked.
5. **Originals and history** distinguish Restore built-in, Restore imported, Follow live source, Cancel pending, Undo last library edit and Undo an accepted story change. Restoring an action definition must preserve unrelated library edits, external books, other chats and accepted story history. Keep exportable backups and revision references so a deliberate shared-source modification can be reversed independently. Show the extent and limits of undo before bulk changes.
6. **Quick Reply file import** inventories visible and hidden entries, triggers, commands, model calls, writes and required state directly from the file. Translate recognized operations into extension actions with explicit timing, scope and cost. Preserve unmapped entries and unknown metadata for inspection and export, identify the missing operation, and offer creation of an editable native equivalent. Importing a file executes zero scripts and registers zero hooks. Supported mappings work with the host Quick Reply extension disabled.

### Create a button directly in any menu

**User decision, 21 November 2026.** Each of the four families is an authoring surface, including when its list is empty. A standalone button lives in the extension library and requires no lorebook, assigned set, native Quick Reply script or particular preset. The user can start from a blank form, duplicate an action as an independent copy, or save a one-off direction they just typed.

| Menu control | Example custom button | Behavior when used |
| --- | --- | --- |
| **Guide a swipe → Add swipe option** | **Let the silence last** — “Give the other character room to sit with what was said.” | Use on a guided regeneration or swipe, alone or with other selected directions and free text. |
| **Continue this reply → Add continuation option** | **Hold the moment** — “Stay with what just happened for one more exchange.” | Append the extra beat to the selected reply. |
| **Draft my reply → Add player draft option** | **Call their bluff** — “Have me challenge one detail I would plausibly recognize.” | Draft only the active player's contribution using the normal persona and knowledge boundaries. Leave the draft editable. |
| **Steer the next reply → Add nudge** | **Remember the audience** — “Let who can overhear this exchange affect what gets said aloud.” | Queue with the next user message. The author can choose a nudge or required instruction and the supported private or visible delivery format. |

The editor starts with **Button name** and **Direction** and inherits the destination from the menu. Offer category, pinning, scope and applicable delivery settings under **Options**. Saving makes the button available immediately. It takes no model call and neither runs nor queues the action. A saved button uses the same search, selection, free-text combination and invocation path as a built-in. Show **Edit** on the action and **Modified** in the list when its saved definition differs from its baseline. Offer named variations, duplicate, reorder, disable, remove and recover. Keep the stable action ID when the name or category changes.

**See changes and put them back.** On an individual button, **Compare changes** shows the original and current label, wording and changed settings, with their scope. Restore offers **Restore built-in**, **Restore first saved version** or **Restore imported version** according to origin. First save establishes a custom button's baseline. Later saves and named variations preserve it. Per-chat overrides offer **Follow library version**. Removing a custom button keeps it recoverable after reload via **Recently removed**. Removing a shipped button hides it until restored.

**Restore a menu or the entire quick-action library.** Preview exactly which items, customizations, visibility, pins and ordering will change. Recommended behavior for **Return to shipped layout** is to restore shipped buttons and archive user-added buttons from that scope, including their variations, so the active menu looks as installed and the user can recover their work. Also offer **Restore built-in buttons only** to keep custom buttons in place. Undo restores the prior configuration. These operations affect button definitions and layout. Already queued directions keep their saved wording and their own Cancel control.

## Preset independence and prompt visibility

The standalone composer, library, local rolls, quick-reply file inspection and draft generation should have no companion-preset-name check. Resolve feature availability using the active host API, chat, current target and available records. A user choosing Memory only can separately opt into explicit quick directions while keeping ordinary automatic writing modules off. Without an eligible story book, offer standalone actions and show where a linked action can be connected. A missing host hook disables the affected destination with a reason; preserve the draft and queue.

Pair editable quick-action prompts with known blocks from the single active preset in the existing workbench. Show provenance, affected turn, role/placement, lifetime and estimated size. Expose independent choices for the quick action and any editable preset block, with optional comparison and per-source restore. Where host inspection is incomplete, show what is known and keep supported actions usable.

## Inspect the player prompt and manage variations

**User decision, 21 November 2026.** Every user-editable extension prompt and preset module gets named variations, individual restore and visible edit status at its point of use. This includes the loaded preset's player impersonation prompt and new user-authored commentator directions and voices. Saving versions of an authoring prompt is independent of the randomized instruction versions that prompt may generate.

### What the user sees in Draft my reply

Show **Impersonation prompt** beside the draft controls, with the active preset/profile name, source and a short status line even when collapsed. Open it to see (1) what the host currently has configured for impersonation, (2) the base instruction this draft will actually use, and (3) the quick-action cues and free text for this invocation. Show matching layers once. Display the editable template with its macros, plus a read-only preview with this chat's substitutions. Preview describes intended input; a receipt after the request can separately identify what was observed. Changing presets or helper profiles refreshes the source and preview and retains pending user input.

For a supported native Chat Completion impersonation, follow the loaded preset by default and let the host supply its base exactly once. For a direct helper, explicitly resolve and include the chosen base once or show the selected extension-owned alternative. Resolve helper wording against that same active preset. If a helper uses a different model connection, show that connection and keep the preset unchanged. Distinguish an explicitly empty host instruction from an unavailable setting. When the host uses a text-formatting cue, show the cue and its owner. Enable edits only through the appropriate writable adapter. An inspectable extension draft template remains available when the host source is opaque. Editing a local draft override is the recommended default; **Edit shared preset** explicitly names the preset and effect on other chats.

### Shared variation controls

Use the same editor in the feature where the prompt is used and in the preset workbench. Cover writing guidance, Write with AI instructions, summary and correction prompts, quick actions, draft and swipe guidance, Roast generation, commentator voice and feedback, ordinary preset blocks, and special host utility fields. Inventory other editable prompt producers outside the main prompt registry during implementation. Keep serialization wrappers and generated user/chat content separate from editable templates.

* **Save as variation** snapshots the current editor contents under a user-chosen name, including a draft the user has not applied. Saving alone leaves the active prompt as it was. **Load variation** previews the difference. **Apply** states the target and scope. Updating an existing variation is explicit. Rename, duplicate, delete with undo, export and import address the selected variation. A selected saved variation can acquire unsaved edits; show its name and edited status separately.
* **Restore extension default** resolves the installed version of that exact extension prompt. **Restore preset original** uses a verified imported or shipped copy of that preset field or block. If only the pre-edit local value is available, label it **Restore before extension edits** and show when it was captured. Offer SillyTavern's own utility default under its own name where available. A newer upstream baseline can be compared before applying it. Restore preserves saved variations; undo restores the previous active value.
* **Block variations** capture the settings the user changed, including wording, role, enabled state, placement, depth, triggers and relative order where the host supports them. Show the affected fields in the diff. Apply against a fresh copy of the active preset, preserving unrelated edits and unknown fields. Never substitute a similarly named block in a different preset. A user may explicitly copy compatible wording into another prompt or preset.
* **New commentator voice** creates a selectable voice with its own name, direction and stable identity. A variation can branch from a shipped voice or a user-created one. “Dry court chronicler” can coexist with “Gremlin” and have its own “Terse” variation. A user-created original is its creation/import snapshot. Voice selection, generating a Roast card, and feeding commentary into later prompts have independent settings. Switching a voice should only change the direction for future applicable requests.
* **Storage and verification.** Persist unexpanded templates and typed block settings, scoped by owning feature or host preset identity, prompt/block ID and baseline revision. Store variations separately from the active selection and temporary drafts. Preserve empty host values, per-owner validation rules, foreign metadata and pre-existing overrides during migration. On external edits, rename/import ambiguity or preset switch during save, re-read the target and offer comparison or explicit relinking. Keep the previous active value on failed validation or write. Preview, save, load, restore and voice creation require zero model calls.

## Fact repair and the recent editing window

**Agreed behavior.** The existing **Correct facts** entry point and the **Fix world facts** switch on guided generation open the same operation. The user may run **Repair facts only**, **Repair and generate swipe**, or an ordinary guided swipe with fact repair off. The combined action uses one submit button. It accepts buttons alone, free text alone through Correct facts, or factual guidance plus stylistic switches. The user can inspect sources and undo changes without having to approve individual rows.

**Audit, propagate, then generate.** The combined action runs the trace against the same evidence used by the story. Resolve the selected chat, turn and swipe. With a supplied truth, trace it to its evidence and known dependent copies, covering scene snapshots, staged facts, committed records, chapter summaries and applicable chat-scoped lore or card corrections. With only the switch selected, audit the focused reply for contradictions against established evidence. This requires a new audit entry path because the present correction API requires a nonempty truth. Prefer an explicit user correction or authoritative source; unresolved disagreement is reported and never promoted to canon by guesswork. Keep style cues out of the persisted correction. For mixed free text, preserve the whole instruction for the swipe and persist only supported factual changes. Propagate verified edits under existing source ownership rules. Shared base books and character cards receive chat-scoped corrections by default. Do not rewrite later player-authored prose automatically.

For an explicitly invoked AI audit, show up to one tracing call plus one ordinary generation if a swipe is requested. Use deterministic provenance replay when sufficient. Show which sources were checked, repaired, protected, unavailable or left unresolved; bounded model excerpts must not produce a claim of exhaustive verification. Give the replacement request the effective corrected state and all selected generation directions. Record the repair separately from the replacement attempt. A failed generation offers **Retry swipe** using the saved correction. Undoing a source repair and changing the selected alternate remain independent.

### Recommended default: keep the current reply and five earlier replies editable

Count accepted character replies in the surviving story timeline, including their associated user input. A swipe replaces a version in one slot, and a continuation extends that slot. Helper calls, previews, aborted attempts and UI/system notices never advance the boundary. Recommended default is six slots total so a user can literally go five character replies back. With replies 1–6, all six are pending. Accepting reply 7 makes only reply 1 eligible to file. Offer the setting under Context & Memory as **Earlier replies kept editable** with the current reply shown separately. This is a proposed filing policy, independent of the chapter interval.

| Layer | When it changes | What reads it |
| --- | --- | --- |
| Per-reply snapshot | Immediately on an accepted reply or selected swipe. Store scene, date/time, weather, cast, emotion, relationships, and supported changes with the turn revision. Save locally across reloads. | The reply's cards, scene editor and source audit. Historical cards use that reply's own revision. |
| Pending story changes | Immediately, in a persisted chat-local journal keyed by stable turn, swipe/revision and source. Include fact additions, changes, retractions and event effects. | The extension builds the current story from the committed book plus surviving pending changes, applying corrections and overrides once. Use that view for next-turn recall, knowledge, plots and corrections. Keep ordinary recall filters and budgets. |
| Physical Story World and dependent summaries | File only validated changes that cross the boundary. Validate source fingerprints and locks again. Checkpoint the book write and journal acknowledgement with an idempotent identifier so retries cannot double-apply it. | Native World Info and external tools reading the physical book can lag behind. In the extension, show **Recent · editable**, **Filed**, and a visible failure/retry status. |

**Automatic edits.** A recent edit, swipe or deletion invalidates the affected revision and its dependent pending changes. Rebuild from the last valid snapshot using surviving evidence and recompute downstream scene cards and the next prompt. Do not replay a parsed update that still depends on removed wording. If the new prose leaves a detail uncertain, drop or mark it stale pending normal extraction; a status badge exposes the uncertainty. Preserve independent facts and user locks. Ordinary recent edits require zero physical book repair calls. A fact independently established or explicitly corrected in an older committed source can still require targeted repair. Trace that source once when requested.

**Boundary cases.** Stage every automatic fact-producing path, including checked events, structured updates and catch-up. An intentional manual book edit or explicit correction of already-filed canon takes effect at once. A short-lived condition that expires or is superseded inside the window should never be filed as still current. Record lasting historical events with their source even if their immediate condition has ended. External book changes during staging require revalidation before filing.

* Chapters summarize and auto-hide only safely filed coverage. Defer a chapter boundary that touches pending material or split it at the stable boundary. Starting a new chapter immediately carries the effective scene and the pending history with provenance into the new chat without forcing early publication, duplicating facts or losing the ability to repair the handoff.
* Branching forks the selected revision's effective history, including only the pending changes through the fork, into its own Story World. A batch deletion can cross the filing boundary. Reconcile committed effects from removed turns through the existing ledger, then establish the new editable window, moving newly exposed recent effects back to pending where provenance permits. Keep this work scoped to affected records.
* Existing installations already contain filed history. Enabling the window cannot silently erase those entries. Apply it prospectively and mark legacy filed turns accurately. A user-invoked rebuild may reconstruct the recent window from verified provenance while preserving manual edits. Catch-up in a new chat should finish with the newest window pending.
* Include pending state in chat persistence and extension backups. Clearly label exports of a physical book as filed-through a particular turn. Tools reading only a physical book see its filed contents even while this extension is enabled. A failed book save leaves the pending revision available for recall and retry.

**Implementation dependencies.** First centralize the correction operation now coordinated in the UI. Then put all automatic world-change producers behind one staged write path and make extension consumers read the effective state. Add promotion, invalidation, branch and chapter handoff before enabling the setting. Attach the same correction operation to both entry points and feed it the effective view. Delaying a save with a timer would not satisfy this design.

## How it ran and which connection it used

Apply the [programmatic execution guideline](../AGENTS.md#prefer-programmatic-execution) to every workflow. Examine code, scripts, macros, native host features and existing structured data before using model output. If the task needs model output, prefer an existing authorized request when it can deliver the result at the right time. Justify any separate request by the specific remaining work it performs.

Every extension output uses the same **How it ran** component, vocabulary and field order. Use a shared compact execution indicator on actions, cards, results, receipts and status messages. Show an extra-call count on the action that starts it, such as **1 model call**. Group execution details at the result level when related items share one path. Use the same icons for code, the reply request and an additional request in every location. Tap the separate execution disclosure to open details with the meaning, trigger, count and connection. Use an accessible disclosure button with expanded state, and make the information reachable by touch, keyboard and screen reader. Opening or closing it preserves the draft, focus and scroll position and makes zero requests. Use the same component in preview mode on controls before they run. List stages individually when an operation mixes code and model work. For example, source matching can run in code, a model can audit the selected excerpts, and a guided swipe can use the ordinary reply request.

| Label | Count | Example |
| --- | --- | --- |
| **Runs in code** | 0 model calls | Roll dice, select a saved nudge, detect repetition, validate evidence, render or restore a card. |
| **Uses the reply request** | 0 additional model calls | Send a nudge, produce structured story state or generate a Roast as part of the NPC reply. A user-requested swipe or continuation starts one ordinary generation. |
| **Additional model request** | Expected count or bounded range before execution, actual attempts afterward | Generate a CYOA batch, trace a correction, write a chapter summary or compare preset prompts. |

Keep call type, call count and connection in the same order everywhere. Before the action show the operation, expected count, trigger and selected connection. Afterward show what ran, actual request attempts, connection used and result, including skipped, failed and cancelled stages. The prior turn's receipt identifies the source of deferred nudges. The next turn's receipt shows whether they were included. The expanded details include plain-text labels. Keep the additional call count visible on the action and put the saved connection in the tap disclosure and the feature’s settings. Show the full automatic trigger and request disclosure beside the enable control. Keep token or price information separate and qualify estimates.

**Authorization.** An additional request requires a clearly labeled user action by default. A compound action can authorize its disclosed steps with one tap. An automatic feature starts disabled for extra requests until explicitly enabled with its trigger, frequency, request budget and connection visible in that same control. Show what happens at reply-count, scene-end or token thresholds for chapter summaries, and what eligible missed instructions or player-agency findings can trigger checks or regeneration. Surface pending and completed automatic work in the same status and receipt components. Explain any existing automatic settings during upgrade and obtain explicit enablement for those whose request behavior was never disclosed. Users can switch automatic requests off independently of code-only tracking and same-reply guidance. Summarizing a chapter manually remains available. Automatic retries count as additional attempts and must fit the disclosed budget. A one-call action with an empty response offers an explicit retry.

**Connection.** Save one connection setting per model-backed function. The default for every function is **Main API**, which uses whichever API and model the host has active when the request starts. A user can choose a named SillyTavern connection profile once in the function’s settings. Store its profile ID and keep using it across invocations, reloads and chat or preset switches until the user changes it. **Use Main API** restores the default for that function. Show the request count by the action and the saved connection in its disclosure. The action runs directly with that setting. The connection selector lives in settings, beside the opt-in for automatic work. Apply the same saved connection to manual and automatic invocations of a function. A compound action shows each model-backed step and uses that step’s saved connection. Work included in the ordinary reply uses that reply’s connection.

Keep the user's selected chat preset active. If a saved profile is missing or unavailable, show the problem in the action status with a direct link to that function’s connection setting. Preserve the draft or pending work and require a deliberate settings change before resuming on a different route. Record the actual resolved connection in the same receipt as the count. Existing explicit profile preferences can be carried into the functions that used them, with their migrated values visible in Settings.

Route each additional request through a shared dispatch policy that identifies its operation, authorization, connection and remaining attempt budget. Include paths that start a host generation, such as optional automatic swipes. Log each model attempt. Audit local actions and inline generation independently so their labels reflect actual execution. Cover current call sites as well as new features.

**Turn lifecycle.** Draft → queued → reserved by one eligible generation → accepted or released. Anchor records to the originating chat and selected swipe, including a content fingerprint so stale drafts can be recognized. A failed or empty generation returns the same reserved choice to pending. A retry should show whether the original request may already have reached a provider. A branch inherits accepted history through its fork point; pending parent directions require explicit copying. Batch deletion or editing invalidates stale receipts/effects through existing history reconciliation. An in-flight draft that finishes after a chat switch goes back to its originating draft store. It must never populate another chat’s composer.

### Guided Generations decisions

Player impersonation uses first person and the player's limited knowledge. For NPC prose, let the model choose who responds in the ordinary request. Supply the latest user contribution, the current scene and up to the five most recent accepted replies on the relevant timeline with their conversational context. A regeneration uses the lead-up to the target; the superseded answer can be supplied separately for revision. A continuation includes the passage being extended. Respect earlier-branch, hidden-history and context boundaries. Where only one plausible respondent is present, use that character. Where several fit, the model can choose an engaging response or introduce a new arrival plausibly. Free text may direct a particular speaker. Keep speaker selection out of the menus and avoid a separate casting call. A host group message may have a host-assigned author; distinguish that message metadata from who speaks in the fiction.
