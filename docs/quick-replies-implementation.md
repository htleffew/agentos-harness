## Build scope and defaults

Use the [readiness recommendations](quick-replies-design.md#pre-implementation-readiness-review) as working defaults. These include a cancellable five-forward-reply Fresh start option with **This action** as the default, a six-slot editable filing window, and automatic historical reconciliation that preserves later prose. They are recommendations for implementation and can be changed in this document if the owner chooses a different policy. The filed chapter threshold starts counting eligible coverage after the last summary, so 20 filed replies with six pending first becomes eligible at accepted reply 26 in a fresh chat. Existing committed entries are retained during migration. Corrections to already committed canon use the existing correction ownership rules.

- First release includes all four guided families, standalone authoring in each, preset-independent source browsing and rolls, on-demand CYOA, Fresh start, shared fact repair, staged memory, next-turn diagnostics, the prompt and preset workbench changes, and execution disclosure across existing and new paths. Each CYOA batch requests **three** playable alternatives in one helper call. Preserve any valid choices from a partial batch and show the actual count. A zero-choice result offers manual recovery and explicit retry. An expansion is a separate, explicit draft action.
- For **Next 5 story replies**, the triggering reply counts as the first of five if it is an accepted forward story reply. A helper, historical swipe or continuation can use Fresh start immediately and still leave five forward slots. A cancelled request spends no slot. If rolling back removes a counted slot, recompute the count from the originating chat's surviving acceptance ledger. A branched chat starts with its own unarmed state.
- One ticket per eligible entry for broad random selection. Resolve version or recipe choices with existing weighting, locks, burn and cycle rules. Manual selection bypasses scheduling chance, waiting and cooldown for that invocation. Disabled items, access restrictions and explicit story locks still apply. Retry retains the draw. Reroll creates a new draw record. Explicitly selecting a source already picked automatically produces a single inclusion and one set of effects.
- Import native lorebook and extension-library JSON using existing readers where applicable. For Keel, inventory all 23 definitions and identify the visible menu and two automatic hooks. Provide explicit, user-selected translations for the five immediate directions and four free-text directions in the inventory, plus **Cancel pending directions** as a shortcut to the queue. Translate the text and intended destination into native action data. Require recognizable source structure and a verified command shape or known fixture, since IDs alone are insufficient. Preserve every original item as data for inspection and export. The remaining scripts, including automatic hooks, stay inert. Link chapter and Notes tools from the extension UI using the existing workflows.
- Exclude concealed delayed queues, ordered scene planning, extra command translations, automatic letter constraints, a full revision-history browser, recurring surprise-writing calls and a second prose rewrite pipeline. The editable local starter name list stays in scope.

## Phone screens

```text
Chat composer                        [Quick actions] [Send]
Quick actions sheet                 [Close]
  Steer the next reply              Guide a swipe
  Continue this reply               Draft my reply
  Pending directions · count       [Review]
  Pinned / Recent
  Search                           [Browse all] [Manage]

Selected family / target            [Back] [Close]
  Pinned and recent directions     [Add option]
  Selected cues in send order      [Remove] [Move up/down]
  Your direction                   multiline input
  Fresh start                      optional disclosure
  Primary action                   [How it ran / execution details]
```

The root sheet opens from the composer. Reply-level controls open the relevant family with the reply name, current swipe and target revision visible. From the composer, a reply-targeted family starts on the latest eligible reply and makes its target visible before sending. Disable an unavailable operation with an explanation. Use a vertically scrolling sheet fitted to the phone viewport, stable header, close/back controls and primary action reachable with the software keyboard up. Keep forms in one column on narrow screens. Maintain stable composer text and selection through opening, closing, failure and chat switching. Tapping an idle favorite can run its labeled primary action. Once text or cues are present, adding a favorite selects it for the single explicit submit. A visible **Customize** opens selection mode at any time.

**Steer** opens with pending count, exact choice or local roll, private or visible delivery, and **Queue with my next message**. **Guide a swipe** displays target and **Fix world facts** before **Generate swipe**. **Continue** displays target and **Continue this reply**. **Draft** gives **Generate my draft** and **Give me choices** primary visibility, with **Impersonation prompt** disclosure beside them. Candidate cards expose **Use this wording**, editing, and, for CYOA, **Draft from this choice**. The manager and editors open from these same screens. Put alternate profiles in persistent per-function settings, with an inspectable execution indicator on every action. Keep visible text on primary controls and provide a regular tap path for reordering, details, removal, restore and Undo.

## Integration contracts

These are boundary contracts. Use existing representations where they meet the contract. Agree on the serialized keys and adapter signatures before parallel workers change shared code.

| Boundary | Inputs and output | Ownership and failure behavior |
| --- | --- | --- |
| Action definition and source resolution | Versioned global library keyed by stable action ID. Store origin, destination family, title, category, editable direction, applicable delivery flags, baseline reference and optional stable source pointer. A resolution returns exact text, source identities, visibility, optional draw record and proposed effects. | Read source records and resolve on a copy. Preview, browse, roll and import inspection make zero model calls. Preview never mutates scheduling state. A missing, changed or ambiguous source offers relink or standalone copy. |
| Queue and invocation | Chat-local pins, pending items and resolved snapshots. Each invocation identifies originating chat, operation, target turn and swipe, revision fingerprint, and attempt. A next-turn item additionally binds to the actual outgoing user contribution before generation. | Reserve at most once per eligible request. Persist the resolved snapshot and retry against the same binding. Commit once on acceptance. Failure releases the reservation without losing wording or inserting visible OOC twice. Hidden prompts, previews, unrelated swipes and auxiliary calls cannot consume the queue. |
| Effective story timeline | Key accepted revisions and append effects by chat, turn, swipe and fingerprint. Overlay surviving pending changes on the filed Story World. Record provenance for both layers. Revision invalidation returns changed or uncertain effects. | Only the shared memory writer promotes eligible accepted changes. A journal acknowledgment and an idempotent book write identity protect retries. Existing explicit locks and manual edits take priority. Branches receive only selected history and their own book. A helper never advances the boundary. |
| History and Fresh start projection | Build request-local context from the targeted timeline, eligible lore and current instructions. For impersonation restrict to player-accessible information. A continuation keeps the exact accepted prefix. A replacement normally has lead-up and, when needed, the superseded answer explicitly labeled as a revision source. Fresh start drops that old version as a prose example where the route supports it. | Capture whether history was substituted or retained. Disclose retained prose before generation and in the receipt. Preserve stored transcript and swipes. Reject a stale target before accepting a result. Mark dependent later state unresolved if surviving evidence is insufficient. |
| Model dispatch and execution receipt | Each operation identifies its ordinary/same-reply or additional request stage, connection setting, authorization, and attempt budget. Receipts include target, outcome, actual attempts and observed route. | Single shared enforcement path for all additional calls, including host swipes triggered automatically and legacy empty-response retries. Per-function **Main API** is default. A missing selected profile blocks that step and preserves the operation for recovery. Inspecting cost never dispatches. |
| Prompt and preset edits | Stable owner and key for each extension prompt, special host field or preset block. Record baseline source and value independently from active edits and named variations. Pair items in native preset order with applicable extension modules. | A single editor contract handles compare, save, named variations and item restore. Verify current scope and host capability before save. The four combined on/off combinations are explicit; the extension records observed delivery separately from requested ownership. Opaque or read-only fields remain identifiable. Parity evaluation is optional and explicitly invoked once. |
| Diagnostics and next-turn input | Accepted prose and the corresponding player contribution feed local phrase, echo, opening, ending and new-name screening. Optional semantic audit is structured metadata from the ordinary reply and cites prior accepted turns. | Recheck evidence against active revisions and count distinct eligible replies in the most recent five. Dispatch concise actionable guidance once with the next eligible reply. Keep avoid-list text and diagnostic evidence examples local. Screening starts zero additional calls. |
