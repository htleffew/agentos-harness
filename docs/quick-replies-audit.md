# Quick replies and guided turns — investigation

Working evidence for the design discussion, 2026-11-21. The baseline is Roleplay Instructions 10.0.32, commit ccd863a. The review covered the six supplied JSON files, the current extension, the native Quick Reply API in the available SillyTavern checkout, and source from four external extensions. This initial inventory comes from reading data and code. The [four-repository follow-up](quick-replies-reference-review.md) traces implementation paths and records isolated SillyTavern exercises and an independent phone-width first-use review. Its verification section identifies the remaining integration work. The uploaded books and scripts were treated as examples and inspected without executing them.

## What the uploaded books actually contain

All five books have an `entries` map and a book-level `extensions.ri.kind`. Individual entries have native World Info properties alongside extension metadata. All ten physical entries have empty primary keys and constant eligibility in these exports. Probability, disabled status, the set limit and extension rules still affect automatic selection. A quick-reply catalog can enumerate their definitions regardless of whether they fired this turn.

Copying the entire entry content into the prompt would lose those semantics. Host cooldown values above are stored values; the extension also translates certain host-message timing values for its reply-based UI. ## Keel v1.9

The file identifies itself as native quick-reply **format version 2**. There are 23 entries. Its one visible anchor opens a menu. The other 22 entries are hidden, including two automatic scripts. The menu, one-shot injections, local variables, global handoff data and generation hooks serve different purposes.

| Entry IDs | Observed behavior | Design candidate |
| --- | --- | --- |
| 10 | A single visible menu dispatches other commands | One compact phone launcher with optional favorites |
| 1, 2, 12, 13, 16 | Five immediate one-turn directions covering a twist, slower pacing and three intensity variants | Individually editable one-shot templates |
| 14, 9, 17, 15 | Skip time, direct the scene, introduce the scene, describe an outfit. These collect direction, with blank input or cancellation handled by individual scripts | Shared input sheet with explicit blank/default and cancel behavior |
| 3, 21 | Cancel the pending nudge or clear pending twist state | Visible pending actions and per-action cancellation |
| 22, 23 | Read objective status and mind notes from Keel variables | Read-only shortcuts to actual extension records, with an empty state |
| 18 | Reset local state, globals and pending injection after a confirmation | Distinguish resetting a shortcut from resetting a story |
| 11, 5, 6, 7, 8 | Chapter menu, generate dossier, generate opening, load into another chat, copy dossier. Writing the dossier and opening are separate generation operations | Link to the existing chapter flow. Show the call count and identity of the destination chat |
| 4 | Select a message range, generate a summary and write a lorebook entry | Reuse chapter coverage, provenance and existing archive controls |
| 19, 20 | After-reply and before-generation hooks use snapshots and `keel_*` variables for objectives, pacing, twists and replacement turns | Reuse the extension’s accepted-reply record and rollback. Map supported imported actions to this extension’s accepted-turn lifecycle |

Several commands address the same ephemeral injection ID, `keel_oneshot`. Treating each button as an independent queued event would change that behavior. The dossier and opening use global handoff variables. An extension-native chapter transfer can bind the transfer to a particular source and destination. Keel's status buttons read state that its other components expect to populate. Importing a label and its text alone cannot recreate that functionality. File conversion and standalone shortcut authoring are distinct features.

## Impersonation prompt ownership and variations

Source inspection on 21 November 2026, using the SillyTavern 1.19.0 checkout. Chat Completion maps the preset field `impersonation_prompt` to the native utility-prompt editor. The host expands macros, constructs an internal system prompt identified as `impersonate`, and adds it to the final control prompts for impersonation generation. An empty string is meaningful. The native restore handler assigns SillyTavern's application default. A preset author may have supplied different wording. Text Completion with Instruct enabled instead selects `last_input_sequence || input_sequence` for its final impersonation cue. These controls have different owners and types. A separate extension helper request does not automatically inherit the native impersonation generation path. ## Native overlap with Pathweaver directing and surprises

The structured turn engine loads enabled instruction/event sets in a loop and proceeds to scene, phase and world processing even when that loop is empty. Memory only returns earlier. On an eligible normal turn it applies the phase multiplier to the autonomous event chance, makes a local roll and considers story-world opportunities. Structured scheduled arcs, seeds, agendas and events use eligibility, weight and spacing. A due time, travel, location or prerequisite can gate them. If neither a structured candidate nor a Story World order is available after the chance check, the engine can offer a scene-appropriate development in the ordinary reply request. Completion requires evidence in the prose. Competition, quiet periods and module settings can suppress an offer. Threats can be tracked through these story records; the structured kind list has no dedicated threat kind. [Turn engine](../src/engine.js) · [Record types, gates and scheduling](../src/v10.js) · [Phases and quiet intervals](../src/pacing.js) · [Story World opportunities](../src/worldflow.js)

## Vexa stock reaction screening

Inspected the uploaded Tavo Vexa 1.0 preset. The four workspace copies have the same SHA-256 prefix `9b84bc66f962`. In its default Chat Completion prompt order, **Prose Rules**, **NPC Voice**, **Prose Lint Functions** and **Banned Vocab** are enabled. The enabled **Antithesis - Tail/Output** has absolute placement at chat depth zero and invokes the previous-reply violation check. The named functions are prompt text interpreted by the model. The embedded regex set has no enabled find pattern matching the inspected jaw, knuckle, sternum, breath-hitch or violation-loop terms by name.

* **Banned Vocab** supplies both a hard word list and a test for what it calls a “receipt beat.” If a beat only confirms the emotional impact of the previous line and deleting it changes nothing, cut it. Otherwise carry the effect into the next line of dialogue or an action. **NPC Voice** separately restricts opening echoes and allows quotes or recaps with an immediate reason. **Prose Rules** asks for consequential action and leaves inferable subtext implicit.
* **Prose Lint Functions** asks for several prior violations unless fewer can be justified, checks repeated structure, and asks how to prevent the findings in the current reply. **Tail/Output** calls that check before prose, asks which banned words to avoid, and explicitly prohibits drafting in the checklist. This is an extended preflight and prior-reply audit. The source alone does not establish whether or how often particular models spend excessive reasoning tokens on it.
* **Candidate for Roleplay Instructions.** Reuse the deletion test and the functional alternatives as compact standing prose guidance. Detect literal wording and known reaction patterns in code and keep matched text in Notes. Use the ordinary reply's structured audit only for recurring patterns that need interpretation. Forward at most the strongest supported finding as a one-use action directive with accurate evidence counts. Request a brief finding only when supported, with no quota. Evaluate rate of echo openings, scene advancement, completion and token use on matched scenes before adding more prompt instructions.
